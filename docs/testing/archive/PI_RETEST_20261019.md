## 已观察的功能问题

### P1 / functional / observed：有效 AV 筛选已落盘，严格验证因默认颜色差异返回 unknown

- 角色：database。
- 最短触发：对 select 列调用 `av.update_view`，筛选值为 `{type:"select",mSelect:[{content:"待办"}]}`，省略默认颜色；先成功预检，再以原参数、requestId `4aeb` 与 expectedStateHash `4d37` 提交。
- 实际结果：`readback_mismatch`，顶层 `transactionState:"unknown"`，cause 为 `Complete verification failed for: filters`。
- 随后只读 `get(scope=view)` 与 `query` 显示筛选已经持久化，查询只剩“说明整理”。主控制器独立原生读回亦保留在 `av-native-after-unknown.json`；`independent-proof.json` 将该任务记为 `failed_strict_receipt`，没有把内容落盘等同安全凭据通过。
- 安全恢复：pi 仅继续两次只读调用，没有换 requestId、重新提交或改入口；网关记录 `frozen.json` 并停止后续角色写入。
- 证据：`ux-database.jsonl:18` 为预检，`:19` 为首次失败，`:20` 和 `:21` 为只读验证；`av-filter-normalization-proof.json` 为离线比较证据。

可以确定的原因：当前 `normalizeAvFilters`（`src/tools/av/view-config.ts:10`）已经归一根 AND 容器，但不规范化嵌套 ValueSelect。使用该函数离线比较原请求与独立原生 AV，唯一差异为 `$.0.filters.0.value.mSelect.0.color` 从缺省变为 `""`。内核 `ValueSelect.Color` JSON 字段没有 omitempty（`sample/siyuan/kernel/av/value.go:2468`），空值会被序列化；`verifyAvTargetConfiguration`（`src/core/write-safety-coordinator.ts:1395`）进行完整比较，因此将该差异判为 filters 不一致。

真实写入观察次数为 **1**，未自动重试。离线差异可确定复算，但不冒充第二次真实复现。建议单独补固定回归：缺省/空/显式颜色的 select 和 mSelect 筛选、嵌套组合、no_change、真正不同颜色与内容仍应被区别。不能粗略丢弃所有颜色或放宽全部 JSON 比较。

## 文档问题

### P2 / docs / observed：链接目标公开 example 缺少 resolve 必需 id

`ux-organizer.jsonl:1` 的 `document.help(topic="ensure_link_targets")` 返回：

```json
{"mode":"resolve","targets":[{"key":"<key>"}]}
```

同一公开帮助明确 resolve/reuse 必须提供已有 ID，该自动 example 不符合实际契约。提示和参数字段中有正确解释，因此这是错误示例问题，不是接口缺少校验。应为 resolve 给出 `{key,id}` 的可执行占位示例，为 create 给出 `{key,title}`；不能同时传入二者。

本轮 pi 并未直接照抄上述 example，因此不能把下一条参数错误直接归因于它。错误示例本身由真实帮助响应确认，未为验证它再执行无意义调用。

## 使用卡点

### P2 / usability / observed：完整 instructions 存在时仍有首次预检遗漏

newcomer 在 `ux-newcomer.jsonl:5`、archivist 在 `archive/ux-archivist.jsonl:6` 首次提交写入均未带 requestId，收到 precondition_required 后才预检恢复。两张任务卡都包含当前公开 strict-write instructions；归档还先读了三个 action help。这证明本轮两个新会话出现了发现/遵循成本，不证明所有用户或模型都会失败。拒绝正确阻止写入，不属于功能失效。

### P2 / usability / observed：链接目标 id/title 互斥容易被当作可附加元数据

organizer 读过帮助后，仍在 resolve 的 targets 同时传 id 和 title，`ux-organizer.jsonl:2` 被明确拒绝。去掉 title 后 resolve/reuse/dryRun 均成功。公开字段已有模式说明，错误信息也足以恢复；可考虑用按模式的 targets oneOf/示例让互斥更直接。当前观察一次。

### P2 / usability / observed：unknown 下模型仍把任务开头标为“完成”

database 最终答复开头为“完成”，随后如实说明 unknown 与只读验证。该答复没有隐藏错误，也没有继续写入，但自动化使用者若只采信完成标签会误读验收状态。正确结论应是“数据内容已读回，严格写入凭据失败，需核对”。模型结论应由控制器的 receipt 与独立读回分类覆盖。

## 测试设施与隔离边界

- **H1 / harness / observed：SQL 网关限制导致额外尝试。** `guard.jsonl:1` 拒绝了带 `root_id=fixture AND id=fixture` 的合法只读查询，dispatched=false。研究角色随后改成网关允许的 root_id 查询成功，COUNT n=3，显式 box 保留。这不是产品 SQL 失败。若继续使用严格 SQL allowlist，应在角色范围说明中提前告知允许的过滤组合，或用能证明作用域的语法分析器。
- **H2 / harness + 参数尝试 / observed：归档首次绝对 basename 被拒绝。** `archive/guard.jsonl:1` 为 `/PI-RECHECK-...-归档模板.md`，改用相对 basename 后成功。该原始路径也不符合产品模板路径约定（应相对路径或 /templates/、/data/templates/），不能标成“网关误拒合法产品调用”。
- **H3 / harness / static_confirmed：第一 broker 的 parentPath/title 路径边界不完整。** 原 broker 只做 startsWith 前缀判断，parentPath 内 `..`、title 带斜杠可能经内核路径归一越出夹具；已及时告知主控制器。`archive/broker.cjs` 后续补了标题单段、反斜杠/`..` 拒绝与规范化路径边界。没有实际利用测试，更不能写成已发生越权。
- **实际轨迹逐项核对无越界。** 第一 broker 控制器所有 create 路径均为本轮 prefix、角色子目录或获批 shadow 笔记本的同路径；pi newcomer 使用本轮 storage parentPath 与标题“第一次会议”；organizer 仅对“方案丙”做 dryRun；数据库只在本轮父文档中建 AV。归档使用独立前缀源文档及唯一模板名。实际已发生的 create/path/title 参数没有 `..` 或反斜杠越界，也没有编辑原用户笔记的证据。
- 公共 instructions 从 `# Working with SiYuan` 截取，未提供原私人规则/记忆；pi 关闭内置 bash/read、其它 MCP、Skills、上下文文件。工具 action 枚举按隔离范围裁剪，help 仍走当前公开契约。因此本轮是受限目标工具中的新会话任务复测，不是完整真实客户端或真人研究，也不是 OS 沙箱保证。
- 全局反链响应在 broker 中还按本轮 ID 做额外过滤；本轮研究角色因此可证明任务来源结果正确，不能单靠这份返回额外证明产品对所有私人来源的原生权限过滤。此前固定真实权限回归的证据应单独引用。
