# SiYuan AI 排版测试手册

这是一份**给 AI 执行**的排版测试文档。

请调用 `siyuan-mcp-sisyphus` 完成排版。

目标不是考察 AI 会不会写普通 Markdown，而是测试 AI 能否根据 MCP 提供的帮助说明，正确判断思源里的不同排版元素、结构语义与富内容类型，并把它们放到合适的形式里。

---

## 1. 执行目标

请新建一篇测试文档，并把这篇文档排版成一份“思源排版能力展示稿”。

要求：

- 最终结果要像一篇结构完整、可阅读的展示文档。
- 思源文档正文只输出最终排版内容，不要解释你是怎么实现的。
- 测试完成后，在对用户的最终报告中额外输出执行摘要与 MCP 提示词缺口记录；这些诊断内容不要写进思源文档正文。
- 如果你不确定某种元素该如何在思源里表达，先读取 MCP 提供的相关帮助资源，再决定实现方式。
- 不要把“能显示出来”当成“语义正确”。本测试更关注元素类型是否选对。

---

## 2. AI 执行规则

1. 优先使用思源原生、语义正确的排版元素。
2. 不要在文档正文里说明具体语法、内部块类型、属性名、底层实现细节或 MCP 推理过程。
3. 不要把以下概念混为一谈：
   - 普通表格 与 结构化数据区
   - 标签 与 收藏语义
   - 一般排版布局 与 并排/卡片式布局
   - 普通代码示例 与 可渲染图形内容
   - 排版结构 与 闪卡语义
   - 普通问答段落 与 真实闪卡
   - Markdown 表格 与 属性视图（AV / 数据库）
4. 每一类元素都要真正出现在文档里，不要只写一句“此处应有某元素”。
5. 文档整体应有统一主题。建议主题为“团队知识库展示页”，但可在不影响测试目标的前提下微调内容题材。
6. 执行过程中维护一份测试日志，尤其记录“首次误调用、看到报错后才修正”的 MCP 调用。

### 2.1 误调用与提示词缺口记录

本测试同时用于检查 MCP 提示是否足够让 AI 一次性选对 action、参数和语义表达。凡是 AI 因提示不清而先调用错，看到报错后才修复，都必须在最终报告中单列。

每条记录至少包含：

- 目标元素或任务，例如 AV、闪卡、嵌入块、可渲染图形
- 首次错误调用的 `tool/action` 与关键参数
- 错误摘要
- 修正后的调用
- 为什么会误判，例如 action 描述不清、字段名不直观、ID 类型不清、help 示例不足、旧用法干扰
- 建议修改 MCP 提示的位置与内容，例如 tool description、action hint、schema description、help 文档或示例

不要把这些诊断信息写入“思源排版能力展示稿”正文；它们只属于测试完成后的外部报告。

---

## 3. 需要完成的排版任务

### 3.1 基础结构区

请至少包含以下内容：

- 一个总标题与简短导语
- 多级标题结构
- 至少 2 段普通段落
- 一组无序列表
- 一组有序列表
- 一组任务清单
- 一个引述内容区
- 一组不同重要程度的信息提示区
- 一段公式展示区
- 一段代码展示区
- 一条分隔元素

### 3.2 行级表达区

请做一个“文本能力示例”区域，至少包含：

- 超链接
- 图片
- 加粗文本
- 倾斜文本
- 下划线文本
- 删除效果文本
- 高亮标记文本
- 上标与下标
- 行内代码
- 小型行内备注
- 标签示例
- 至少一组层级标签示例
- 至少两种不同的颜色或强调效果
- 至少 3 个表情字符

### 3.3 复合布局区

请做一个“信息对照展示”区域，至少包含：

- 一个左右并排的双栏区域
- 一个包含 4 个内容单元的卡片式区域
- 一个适合放摘要或对比信息的嵌套布局区域
- 一个会展示动态查询结果的区域

注意：这里测试的是布局是否正确，不是文字是否华丽。

### 3.4 图形与可渲染内容区

请做一个“可视化展示”章节，至少包含以下内容中的每一项：

- 脑图
- 流程图
- 时序图
- 甘特图
- 类关系图
- 用户游历图
- Git 历史图
- 实体关系图
- 图表
- 五线谱
- 一种 Graphviz 图
- 一种 PlantUML 图

要求这些内容在最终文档中应被视为可渲染的结构化内容，而不是普通代码样例堆砌。

### 3.5 富媒体与嵌入区

请增加一个“富内容展示”章节，至少包含：

- 一段 HTML 内容
- 一个外部嵌入区域
- 一个视频内容区
- 一个音频内容区

### 3.6 轻量结构化展示区

请增加一个“数据整理”章节，至少包含：

- 一个轻量的二维信息展示区，用于展示少量字段
- 一个真正用于记录结构化条目的区域，用于展示多条记录；该区域必须使用思源属性视图（AV / 数据库），不能用 Markdown 表格冒充

这两者都要出现，但不要把它们做成同一种东西。

属性视图（AV / 数据库）要求：

- 必须创建一个真实 AV，并把它嵌入本轮测试文档
- 至少包含 3 条记录
- 至少包含主键列之外的 2 个字段，例如状态、负责人、优先级、日期、标签或备注
- 至少写入一次单元格值，能看出字段类型和记录内容是结构化的
- 可选：新增一条纯文本主键的 detached 行，用于验证不依赖已有块也能形成记录
- 不要把 AV 解释成普通二维表；二维表和 AV 必须同时出现、语义不同

### 3.7 语义能力区

请增加一个“知识管理语义”章节，至少包含：

- 一个适合后续检索的标签使用示例
- 一个适合“收藏 / 稍后查看 / 收集已有内容”的示例
- 一个带有补充说明的块级信息样例
- 一组与复习相关的内容，其中至少体现 2 种不同的问答/记忆组织方式；该组内容必须被登记为真实闪卡，不能只是普通问答文本

注意：这里测试的是“语义是否放对位置”，不是只看视觉效果。

闪卡要求：

- 必须创建或使用一个可用 deck，并把本轮测试文档中的至少 2 个块加入闪卡
- 至少包含 2 种组织方式，例如基础问答、挖空/提示、概念辨析、步骤回忆
- 闪卡来源块应保留在文档中，并能从正文语义上看出它们是用于复习的内容
- 如环境无法创建或写入闪卡，应标记为受环境限制，不得用普通段落宣称已完成闪卡测试

---

## 4. 验收重点

完成后，请自行检查结果是否满足以下要求：

1. 所有大类元素都已实际落地。
2. 没有把相近概念错误替代。
3. 没有把本该是结构化内容的部分退化成普通段落。
4. 没有把本该是排版结构的问题误当成样式问题。
5. 没有把本该是语义标记的问题误当成普通文本装饰。
6. 文档整体可读、分区清晰，不是零散元素罗列。
7. AV 区域是真实属性视图，闪卡区域是真实登记的 flashcard，不是视觉替代。
8. 如果出现报错后修正的调用，最终报告中有明确的 MCP 提示词缺口分析与修改建议。

---

## 5. 判定标准

如果 AI 只是做出“看起来差不多”的效果，但元素类型、组织方式或语义归类不正确，则本轮测试应视为**不通过**。

如果 AI 能够根据 MCP 帮助资源，把这些元素放到正确的思源表达方式中，同时避免常见混淆，则可视为**通过**。

---

## 6. 最终报告要求

测试完成后，对用户输出一份外部报告。报告不要写入思源测试文档正文。

报告至少包含：

- 测试文档 ID / 路径
- 已完成的大类元素清单
- AV 完成情况：AV ID、数据库块 ID、记录数、字段数、是否包含 detached 行
- Flashcard 完成情况：deck ID、加入闪卡的块 ID、组织方式数量；如受环境限制，说明阻塞原因
- 未完成或降级实现的项目
- 清理策略或保留说明

### 6.1 MCP 提示词缺口与建议修改

必须输出本轮“首次误调用、看到报错后才修正”的记录。如果没有，写“未发现”。

每条记录建议使用以下格式：

| 项 | 内容 |
| --- | --- |
| 目标 | 要实现的排版 / 语义能力 |
| 误调用 | 首次错误的 `tool/action` 与关键参数 |
| 报错 | 错误摘要 |
| 修正 | 修正后的调用 |
| 误判原因 | 为什么 MCP 提示没有让 AI 一次选对 |
| 建议修改 | 建议改哪个提示、schema 描述、help 或示例 |

建议修改必须具体，例如：

- “`av.query` 的帮助应说明创建 AV 时 `blockID` 是父级插入块；后续 AV 写操作通常可只传 `avID`，由 MCP 自动从行绑定、镜像数据库块或 AV 块记录解析 owning database block。”
- “`flashcard.create_card` 的帮助应说明它登记的是已有块，不会自动把普通问答段落变成卡片内容。”
- “可渲染图形相关帮助应明确哪些内容适合 code block，哪些需要思源原生图形块或嵌入块。”
